# Jira report from current chat

## Purpose
現在のチャット内容をもとに、Jira チケットのコメント欄に記載できる作業報告ドラフトを作成し、ユーザー承認後またはユーザー手入力後に登録先の Jira チケット ID を確認して、投稿用の最終コメントを確定する。

この skill の役割は以下を含む。
1. 現在のチャットから、作業報告として使える内容を抽出する
2. Jira コメント向けに簡潔な文章へ整形する
3. ユーザーにドラフト案を提示し、承認・修正・手入力のいずれかを選べるようにする
4. 承認後、または手入力本文確定後に Jira チケット ID の入力を促す
5. チケット ID を受け取ったら、投稿用の最終確認文を返す
6. 必要に応じて、外部スクリプトまたは別ツールへ渡すための入力を整える

この skill 自体が Jira 投稿機能を直接持たない場合は、投稿処理は外部スクリプトまたは別ツールに委譲する。
ただし、ユーザー体験としては一連の流れをこの skill が案内する。

## When to use
次のような依頼があったときに使う。

- このチャットからjiraレポートを作ってください
- この会話をJiraコメント用にまとめてください
- 今日のやり取りを Jira に書ける形にしてください
- このチャットを作業報告にしてください

同じ意図であれば、多少表現が異なっても適用してよい。

## Inputs
主な入力は以下。

- 現在のチャット履歴
- この会話の中で言及された作業内容
- この会話の中で明示された実施結果、課題、次アクション
- ユーザーから後続で与えられる承認メッセージ
- ユーザーから後続で与えられる修正指示
- ユーザーから後続で与えられる手入力レポート本文
- ユーザーから後続で与えられる Jira チケット ID

## State handling
この skill は会話の流れに応じて、次の状態を扱う。

### State 1: Draft creation
まだレポート案が承認されていない状態。
この状態では、現在のチャットから Jira コメント案を作成して提示する。

### State 2: Waiting for approval or revision choice
ドラフト提示後、ユーザーの応答を待つ状態。
この状態では、ユーザーは次のいずれかを選べる。
- 承認する
- 修正を依頼する
- 手入力に切り替える

### State 3: Waiting for user-written report
ユーザーが「手入力」を選んだ後の状態。
この状態では、ユーザーが入力した本文を Jira コメント本文候補として扱う。

### State 4: Waiting for ticket ID
ドラフトが承認された後、または手入力本文が確定した後、登録先の Jira チケット ID を待つ状態。

### State 5: Ready to post
チケット ID を受け取った後の状態。
この状態では、投稿対象チケットとコメント本文を明示し、投稿処理に進める形に整える。

## Rules
以下のルールを必ず守ること。

1. 推測で事実を補完しない
2. チャット内で確認できる内容だけを材料にする
3. 実施済みの内容と、検討中の内容を混同しない
4. 実装したか不明な内容は断定しない
5. チャット内で相談しただけの内容は、実施済みとして書かず、必要に応じて「調査」「整理」「検討」と表現する
6. 試行錯誤の細かい過程はそのまま列挙せず、報告に必要な粒度へ要約する
7. 雑談や本筋でない話題は含めない
8. Jira コメントとして自然で簡潔な日本語にする
9. 必要以上に長文化しない
10. 不明点が多い場合でも、まずは利用可能な情報だけでドラフト案を作る
11. 承認されるまでは Jira チケット ID を聞かない
12. 各セクションの箇条書きは原則 3 項目以内に収める
13. ユーザーが修正を求めた場合は、その指示を反映してドラフトを更新する
14. 投稿前には、投稿対象チケット ID とコメント内容を明示する
15. 投稿処理を行う場合は、ユーザーの承認または手入力本文の確定と、チケット ID の両方が揃ってから進める
16. ユーザーがレポート案を承認しない場合、「修正依頼」または「手入力」のフローを案内する
17. ユーザーが「手入力」と指定した場合は、ユーザーが次に送る本文を Jira コメント本文の候補として扱う
18. 手入力された本文は原則としてそのまま尊重し、意味を変える編集をしない
19. 手入力本文に軽微な整形を加えた場合は、その旨を簡潔に伝える
20. 手入力本文を受け取った後は、その本文を確定候補として Jira チケット ID の確認へ進む
21. Jira チケット ID の形式が不明でも勝手に補正しない
22. 投稿実行は、ユーザーが明示的に「登録して」などの実行意思を示した場合に限る

## Content selection policy
優先して拾う内容:
- 実際に対応した内容
- 判断や方針決定
- 問題点とその整理
- 未解決事項
- 次にやること

優先しない内容:
- 単なる思いつき
- 雑談
- 実行されていない案
- 根拠のない推測

## Writing style
文体は、業務用の簡潔な報告スタイルとする。

- 箇条書きを基本とする
- 1項目は長くても 1〜2 文に抑える
- 読み手が進捗をすぐ把握できる形にする
- 断定しすぎず、曖昧すぎない表現を使う

## Output format for draft
ドラフト提示時は、必ず次の形式で出力する。

対応内容
- ...
- ...

実施結果
- ...
- ...

課題・懸念
- ...
- ...

次アクション
- ...
- ...

最後に、次の趣旨の案内文を添える。

- この内容で問題なければ「承認」と返してください。
- 修正したい場合は修正内容を指示してください。
- レポートを自分で入力する場合は「手入力」と返してください。
- 承認後、または手入力本文の確定後に、登録先の Jira チケット ID を確認します。

## Approval handling
ドラフト提示後は、ユーザーの応答を待つ。

次の 3 パターンを受け付ける。
- 承認する
- 修正を依頼する
- 手入力に切り替える

承認として扱う例:
- 承認
- OK
- この内容でいいです
- 問題ありません

手入力への切り替えとして扱う例:
- 手入力
- 自分で入力します
- 自分で書きます
- 別の文面を入れたいです

承認が得られた場合は、次のように返す。
- 承認ありがとうございます。登録先の Jira チケット ID を教えてください。

修正依頼が来た場合は、その指示を反映してドラフトを再生成する。

手入力が指定された場合は、次のように返す。
- 承知しました。登録したい Jira コメント本文をそのまま入力してください。入力内容をレポート本文として扱います。

## User-written report handling
ユーザーが「手入力」を選んだ場合は、次に送られる本文を Jira コメント本文候補として扱う。

このときのルール:
- 本文は原則そのまま尊重する
- 意味を変える編集はしない
- 必要なら改行や箇条書きなどの軽微な整形のみ行う
- 整形した場合は、その旨を簡潔に伝える

本文受領後は、次のように案内する。
- レポート本文を受け取りました。登録先の Jira チケット ID を教えてください。

## Ticket ID handling
承認後、または手入力本文確定後に Jira チケット ID が与えられた場合は、次の情報を整理して返す。

- 投稿先チケット ID
- 投稿するコメント本文
- 投稿実行の最終確認

たとえば次のように返す。

登録先: ABC-123

投稿コメント:
対応内容
- ...
- ...

実施結果
- ...
- ...

課題・懸念
- ...
- ...

次アクション
- ...
- ...

この内容を ABC-123 に登録します。問題なければ「登録して」と返してください。

手入力本文を採用した場合も同様に、本文をそのまま使って最終確認を行う。

ユーザーが「登録して」など、明示的に投稿実行を指示した場合は、利用可能な外部スクリプトまたはツールへ次の情報を渡す。

- ticket_id
- comment_body
